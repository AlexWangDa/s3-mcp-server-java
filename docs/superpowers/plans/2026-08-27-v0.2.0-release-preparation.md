# S3 MCP Server v0.2.0 Release Preparation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the verified `0.2.0-SNAPSHOT` build into a consistent v0.2.0 release candidate with human-readable release notes and a tag-triggered GitHub Release workflow.

**Architecture:** Release identity has one canonical value, `0.2.0`, repeated only where Maven, MCP metadata, executable-JAR tests, and copyable documentation require it. A GitHub Actions workflow validates that a pushed `vX.Y.Z` tag exactly matches the non-snapshot Maven version, runs the full Docker-backed verification suite, creates a SHA-256 checksum, and publishes both files through the GitHub CLI.

**Tech Stack:** Maven Wrapper 3.9.11, Java 17, Spring Boot 4.1.1, Spring AI 2.0.0, GitHub Actions, GitHub CLI, Testcontainers, MinIO

**Spec:** `docs/superpowers/specs/2026-08-26-v0.2.0-stabilization-design.md`

## Global Constraints

- Preserve the existing eight MCP tool names and all v0.2.0 behavior defined by the stabilization spec.
- Keep Java 17 as the compilation floor and verify Linux builds on Java 17 and 21.
- Use the checked-in Maven Wrapper; do not require a system Maven installation.
- Run unit, MinIO, and packaged STDIO tests without external cloud credentials.
- Keep MCP protocol traffic on stdout and diagnostics on stderr or the configured log file.
- Change release-facing `0.2.0-SNAPSHOT` values to exactly `0.2.0`; historical specs and plans remain unchanged.
- Trigger publishing only from a pushed `v*` tag whose name is exactly `v${project.version}`.
- Do not create or push a tag, and do not publish a GitHub Release as part of this plan.
- Do not add delete, copy, move, batch, multipart, HTTP transport, native-image, or container distribution features.

### Task 2: Tag-Triggered GitHub Release Workflow

**Files:**
- Create: `.github/workflows/release.yml`

**Interfaces:**
- Consumes: pushed tag in `GITHUB_REF_NAME`, Maven `project.version`, executable `target/s3-mcp-server-${version}.jar`, and repository-scoped `github.token`.
- Produces: a GitHub Release named `v${version}` containing the executable JAR and `s3-mcp-server-${version}.jar.sha256`.

- [x] **Step 1: Run the workflow contract and verify it fails**

```bash
  .github/workflows/release.yml

rg -q './mvnw -B clean verify' .github/workflows/release.yml

rg -q 'gh release create' .github/workflows/release.yml
```

Expected: FAIL because `.github/workflows/release.yml` does not exist.

- [x] **Step 2: Add the release workflow**

Create `.github/workflows/release.yml` with a `push.tags: ['v*']` trigger, `contents: write` permission, and one Ubuntu job. Use `actions/checkout@v4` with `persist-credentials: false`, `actions/setup-java@v4`, Temurin 17, and Maven caching. The job must run these operations in order:

```bash
version="$(./mvnw help:evaluate -Dexpression=project.version -q -DforceStdout)"
test "${version#*-SNAPSHOT}" = "$version"
test "$GITHUB_REF_NAME" = "v${version}"
./mvnw -B clean verify
artifact="s3-mcp-server-${version}.jar"
test -f "target/${artifact}"
(
  cd target
  sha256sum "$artifact" > "${artifact}.sha256"
)
gh release create "$GITHUB_REF_NAME" \
  "target/${artifact}" "target/${artifact}.sha256" \
  --verify-tag --generate-notes --title "v${version}"
```

Export `version` through the version step's `GITHUB_OUTPUT`, pass it to later steps as `VERSION`, and pass `${{ github.token }}` as `GH_TOKEN` only to the publish step. Add concurrency group `release-${{ github.ref }}` with `cancel-in-progress: false` so the same tag cannot publish concurrently.
